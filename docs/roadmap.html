Analysis and roadmap

Where the library stands against the goal: a self-consistent model of a small world that completes itself logically, explains itself, and can be learned from examples.

What is settled

These decisions held through four iterations and the tests rely on them. Treat them as the architecture.

  • One language. Facts, schema, rules and constraints are all wires. A matrix can be stored, sent, diffed and learned like data.
  • One operation. Every change is a transaction of ingest, chase, validate. Dry runs, completion search, abduction checks and what-if trials are the same operation on a state that is rolled back.
  • Declarative rules, named code. Functions are the only place for code.
  • Open world, explicit questions. Missing is unknown. Required keys make the unknown visible as questions.
  • Provenance on everything. Wires, values and rule firings record their sources. Explanation, incremental retraction, revision of assumptions and the conflict analysis of the solvers all read that record.
  • Three strengths of belief. Told, derived or forced, and assumed. Only assumptions give way.
  • The world is the judge. Search is a strategy. Whatever a solver proposes, built in or outside, is accepted only after the world has verified it.
  • One file. The sources are small modules; the product is one file that runs unchanged in Node and in a browser.

Is a neural part needed

Not for validity. Matching, completion, search, abduction, induction and revision are symbolic and exact. A statistical part earns its place at four edges, and the library has a seam for each:

EdgeSeam in the library
Text to wirestell accepts wire objects; refusals come back as data, with the told wires they rest on
Wires to textcore.question wires carry ask, options and the wire they are about
Which of several consistent options is likelyrank option, cost on abducibles
Fuzzy equality of atomsA custom core.check function

Recommended order of work

  1. Formaliser contract. Fix the loop of propose wires, read violations and their support, repair. It decides how good completion feels in a real chat, and it needs no engine change.
  2. Contexts. core.in=$ctx with rules that hold per context: nested worlds, hypothetical branches, per-speaker beliefs.
  3. Grounding of rule consequences. So that the solver sees conflicts that arise through rules before it proposes an answer.
  4. Match network. Only when a real matrix shows the need; measure first with npm run bench.
  5. Induction with scoring. Noise and learned negation, using the world itself as the judge of candidate rules.

How to judge progress

  • Every new capability lands with a small world in examples/ and a test that states the expected wires.
  • Anything incremental is tested against a rebuild from scratch; every solver against a reference solver.
  • The suite must pass on the sources and on the built file, and the self-test in a browser.
  • A matrix written by a person for a new domain should need no change in src/. When it does, that is the next item for this page.
