The kinds of worlds, and where code lives

There are three kinds of worlds, plus the library's modules (the names are defined in the glossary). This page says what each kind may contain, how they combine at run time, and where a piece of code belongs. Every example runs in CI.

1. World schema

A world schema says what a kind of world is. It may contain:

  • kinds of things (core.type ... extends=std.schema.thing) and their attributes: slots with value types, ranges, steps, defaults and the question to ask when one is open;
  • slot groups (several extends), excludes= pairs and joins to another world (type=T by=name);
  • count limits (std.schema.limit) and capacities (std.schema.capacity);
  • which acts apply to which kind (std.schema.kind ... acts=), the aspects and views;
  • rules and denies, and the words for all of it (core.word).

It names the functions it uses and does not contain them. Pure functions come from the standard pack (builtins: arithmetic, comparisons, boxes, dates and the rest; listed in the reference). Effects are implemented by the application and declared in the schema (std.schema.effect of= act= action=). A world schema holds no particular things and no code.

2. Knowledge world

A knowledge world holds facts about the world at large, true for everyone. It may contain:

  • facts (k.animal name=fish lives=water);
  • constraints (slots, excludes, joins);
  • rules that derive more facts: habitat to usual place, carried things go with their carrier, "is a kind of" chains;
  • the provenance of every fact (core.source), including facts labelled by a model.

It has no session state and no code. When a rule needs a computation the pack lacks, ask for a function in the library (a general one goes into the standard pack); do not embed code in the world.

3. Live world

A live world is an instance of world schemas in a session. It holds the state (the things made and their values), the focus, the history and undo, and the views that show it. It inherits the constraints and rules of its schemas and reads knowledge worlds by lookup (createCatalog, createCatalogs, std.know.fill, std.schema.needs). The application's tools (renderers, engines, editors) are attached through effects.

The library keeps state and view consistent. Every act returns the difference it made to the state (diff), which is what the view re-renders, and an effect's difference comes back in diff.effects. What is rendered is the state, never something kept beside it.

4. Library modules

The std.* modules are mechanisms, not worlds. Each serves one kind:

ModuleServes
std.schemawriting a world schema
std.know, createCatalog, createCatalogsreading knowledge worlds into a live world
std.acts, std.fill, std.focus, std.relations, std.turn (turn, turnFlow)running a live world
the grammar reader (grammarOf, parseText, nounPhrase), resolvereading a language's knowledge world, then a live world
std.numbers, std.order, std.boxes, builtinspure functions any world names

5. Where code lives

World schemas and knowledge worlds stay SOP Lang only, so any application can reuse them. A general function goes into the library's standard pack. A specific tool stays in the application and is connected through a declared effect. Three examples:

A needWhere it ends up
"two boxes must not overlap"the pack already has overlaps; the world schema writes a deny that names it
"the median of the scores"a general computation: median in std.numbers, named by any world
"draw the face on the canvas"the application's renderer, connected by std.schema.effect of=face act=change action=draw
